# Compare the layer, not the logo

A Docker Sandbox Kit is a **portable definition and OCI artifact**, not compute: its image carries a filesystem plus typed authority requests, and a supporting runtime interprets those requests ([Kit v3 overview and boundary](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#1-overview)). `sbx` is Docker’s actual execution product: it creates and manages local or Docker-managed cloud sandboxes ([Docker Sandboxes](https://docs.docker.com/ai/sandboxes/)).

| Layer | Closest comparisons | What is actually comparable |
|---|---|---|
| **Environment definition** | **Dev Containers** describes a dev environment using `devcontainer.json` or metadata in an image label; it supports features, mounts, ports, and setup hooks ([spec](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainer-reference.md)). Kits likewise ride on OCI images, but put typed, versioned host requests in the manifest and define a permission surface that hosts can gate on updates ([Kit capabilities](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#7-capabilities), [gate](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#74-permission-surface-and-the-gate)). | Tool and image portability; permission declaration and approval semantics; which runtime implements the contract. |
| **Sandbox execution** | Compare Docker **Sandboxes/`sbx`** with **E2B**, whose SDK creates on-demand Linux VMs from templates and supports pause/resume ([docs](https://docs.e2b.dev/)), and **Daytona**, whose API/SDK/CLI manages isolated container or VM sandboxes ([docs](https://www.daytona.io/docs/en/sandboxes)). | Isolation boundary; authority and credential enforcement; startup, persistence, lifecycle APIs; local versus hosted deployment and prerequisites. |
| **Fleet orchestration** | **Google AX** declares Tasks, Workspaces, and Models ([overview](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#why)); its controllers reconcile tasks onto Agent Substrate actors and expose suspend/resume ([design](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/DESIGN.md#architecture)). It requires Kubernetes plus Agent Substrate ([prerequisites](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#prerequisites)). | Task scheduling, reconciliation, fleet lifecycle, scale, and operator burden—not Kit artifact portability. |

**Decision:** For a repeatable development shell, start with Dev Containers. For an agent sandbox whose tools carry explicit network and credential requests, evaluate Kits with `sbx` ([Kit permissions](permissions.md)). For hosted execution, compare Docker Cloud Sandboxes, E2B, and Daytona on isolation class, network/secret controls, lifecycle API, persistence, and cost ([Docker cloud](https://docs.docker.com/ai/sandboxes-api/), [E2B](https://docs.e2b.dev/), [Daytona](https://www.daytona.io/docs/en/sandboxes)). For reconciliation of many tasks on your own Kubernetes/Agent Substrate cluster, consider AX ([AX comparison](compare-ax.md)). These are choices at different layers, not one feature ranking.
