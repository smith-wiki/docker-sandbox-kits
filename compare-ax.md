# Docker Kits package authority requests; AX operates task lifecycles

> Compared snapshots: [`docker/sandbox-kit-spec` `5fabb0a` (2026-09-25)](https://github.com/docker/sandbox-kit-spec/tree/5fabb0a260db4fded6c2f2da76e89b7582c9b536) and [`google/ax` `e09ed1b` (2026-09-24)](https://github.com/google/ax/tree/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7).

A Docker Sandbox Kit is a **packaged artifact**: one ordinary OCI image whose layers contain a workload or mixin and whose manifest annotation declares its requirements. Those capabilities are requests to the host, not powers the image grants itself; a conforming runtime supplies their behavior, while an engine that ignores the annotation runs only an ordinary image ([v3 overview](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#1-overview), [capability boundary](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#13-where-behavior-is-specified)). Docker’s `sbx` provides a local microVM boundary and mediates shared files, network, and credentials ([security model](https://docs.docker.com/ai/sandboxes/security/)), but it currently does not apply three v3 capability types and may still create a sandbox when an unsupported request is required ([implementation limits](https://docs.docker.com/ai/sandboxes/customize/author/#capabilities)). See [the artifact model](what-are-kits.md), [composition](composition.md), and [permissions](permissions.md).

AX is an **orchestrator**. A `Task` declares an image, command, and Workspace bindings. A `Workspace` declares Git and tool setup, but the default runner does not yet materialize every declared MCP/skill integration. A `Model` is platform-level provider configuration, not automatically the task agent's model ([concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md), [setup code](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/internal/workspace/setup.go#L76-L127), [Task schema](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto#L70-L90)).

Its server stores desired state in Redis; controllers consume Redis Streams and drive Agent Substrate actors through create, watch, suspend, resume, and delete ([design](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/DESIGN.md#architecture)). Substrate supplies isolation; enabling AX debug services permits arbitrary process execution and file access inside the sandbox ([sandbox guide](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/sandbox.md#guest-services)).
AX is still pre-stable: upstream warns that core concepts, protocols, and specifications may change substantially, and its public resources remain `ax.io/v1alpha1` ([status](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L6-L13)).

No native Kit–AX integration is documented in either snapshot ([AX prerequisites](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/README.md#L61-L65), [Docker integrations](https://docs.docker.com/ai/sandboxes/integrations/)). AX requires its runner contract inside a task image, and AX does not claim to interpret or enforce Kit annotations ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md#how-a-runner-is-launched)). Choose Kits plus `sbx` for a reproducible, policy-reviewed **laptop sandbox** ([try it](try-it.md)); choose AX when the problem is **fleet lifecycle and reconciliation** on an existing Kubernetes–Substrate cluster. For AX’s maturity and operational caveats, read [the AX research](https://smith.wiki/google-ax/what-is-ax.html).
