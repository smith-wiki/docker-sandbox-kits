# Same placeholder pattern, different documented checks and storage

This comparison uses the **local TLS path**. Docker scopes this credential store and proxy flow to local Sandboxes and configures cloud credentials separately ([Docker scope](https://docs.docker.com/ai/sandboxes/configuration/credentials/)). microsandbox says hostname-scoped substitution works on local and cloud backends, but cloud does not accept TLS-interception or host-CA-trust configuration; its public docs do not describe a cloud counterpart to the local interception mechanism. The CA, DNS, SNI, and authority chain below therefore applies only to the documented local path ([microsandbox cloud compatibility](https://docs.microsandbox.dev/cloud/overview#compatibility), [local TLS mechanism](https://docs.microsandbox.dev/networking/tls#how-it-works)).

Both systems can keep a service credential out of the VM without making the service unusable. The guest gets a sentinel, sends it in an outbound request, and a host-side proxy substitutes the real value only for an approved destination; the upstream API therefore authenticates the request even though guest code never held the value ([microsandbox data flow](https://docs.microsandbox.dev/security/secrets#the-data-flow), [Docker injection flow](https://docs.docker.com/ai/sandboxes/configuration/credentials/#how-credential-injection-works)). See [Docker’s six-step request path](secret-injection-flow.md) for that side alone.

| Question | microsandbox local TLS path | Local Docker Sandboxes |
| --- | --- | --- |
| What is inside the guest? | The bound environment variable contains `$MSB_<name>` or a custom placeholder, not the value ([Secrets](https://docs.microsandbox.dev/sandboxes/secrets#add-a-secret)). | A named proxy-managed `credential@1` API key gets a sentinel; an inject-only declaration has no environment presence at all ([Kit contract](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior)). |
| When may the proxy substitute? | By default, intercepted TLS must pass the allowed-SNI match, observed-DNS-to-IP pin, and HTTP `Host`/`:authority` alignment. The proxy CA is trusted by the guest; the proxy opens a separate upstream TLS connection and verifies its certificate by default, although configuration can explicitly relax that verification ([substitution gates](https://docs.microsandbox.dev/security/secrets#what-gates-a-substitution), [TLS flow and upstream trust](https://docs.microsandbox.dev/networking/tls#how-it-works)). | The Kit names a service, phase, allowed injection domain, header, and format; the host proxy matches the declared service/destination and overwrites the auth header ([Docker flow](https://docs.docker.com/ai/sandboxes/configuration/credentials/#how-credential-injection-works), [`credential@1`](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#config)). The consulted Docker credential docs and Kit contract do **not document whether** Docker applies microsandbox’s exact CA, DNS-pin, SNI, and authority checks; that is not a claim that Docker lacks them. |
| Which request parts are rewritten? | Headers, including Basic auth, are enabled by default; query strings and bodies are explicit opt-ins, and body rewriting has protocol, encoding, and size limits ([request locations](https://docs.microsandbox.dev/sandboxes/secrets#request-locations), [SDK limits](https://docs.microsandbox.dev/sdk/typescript/secrets#secret-substituteinbody)). | Kit `credential@1` describes domain-targeted header/format rules. Although the specification also defines `scheme`/Basic-auth fields, current `sbx` documentation says v3 Kits do not use `apiKey.inject[].scheme`. Separately, experimental `sbx secret set-custom` replaces its placeholder “anywhere in the request” for configured hosts and is intended for cases such as request bodies ([Kit fields](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#config), [current `sbx` support](https://docs.docker.com/ai/sandboxes/configuration/credentials/#services-declared-by-kits), [custom secrets](https://docs.docker.com/ai/sandboxes/configuration/credentials/#custom-secrets)). |
| What if a placeholder is detected but is not eligible? | The default is block-and-log; alternatives are silent block, block-and-terminate, or host-scoped passthrough of the unchanged placeholder. Opaque bypassed TLS cannot be inspected for placeholders ([violation policy](https://docs.microsandbox.dev/sandboxes/secrets#violation-policy), [boundary](https://docs.microsandbox.dev/security/secrets#what-gates-a-substitution)). | The consulted Docker sources promise substitution only on matching rules, but do not specify an equivalent invalid-placeholder violation-policy matrix ([Docker flow](https://docs.docker.com/ai/sandboxes/configuration/credentials/#how-credential-injection-works), [`credential@1` runtime behavior](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior)). |
| Where is the host-side value persisted? | Supplying SDK `value` persists it **verbatim in the durable host-side sandbox configuration**, and stopping the sandbox does not remove it. The CLI stores a host-environment reference and reads it at startup; inline CLI values are rejected. An exact YAML environment reference likewise avoids persisting the resolved value ([add a secret](https://docs.microsandbox.dev/sandboxes/secrets#add-a-secret), [TypeScript SDK warning](https://docs.microsandbox.dev/sdk/typescript/secrets#sandboxbuilder-secretenv), [YAML configuration](https://docs.microsandbox.dev/sandboxes/secrets#yaml-configuration)). | `sbx secret set` stores local values in the OS credential store—macOS Keychain, Windows Credential Manager, or Linux Secret Service—with a permission-protected file fallback on Linux without Secret Service. Dynamic sources store the reference or command rather than the credential ([Docker storage](https://docs.docker.com/ai/sandboxes/configuration/credentials/#where-secrets-are-stored), [dynamic sources](https://docs.docker.com/ai/sandboxes/configuration/credentials/#use-a-dynamic-secret-source)). |

The microsandbox destination checks are a documented product guarantee for its inspected local path; Docker’s normative Kit promise is narrower: a conforming runtime must keep proxy-managed values out of the container and substitute them for matching rules. Current `sbx` storage and custom-secret behavior are Docker implementation documentation, not additional fields in the portable Kit contract ([microsandbox secret boundary](https://docs.microsandbox.dev/security/secrets), [`credential@1` runtime behavior](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior), [Docker custom secrets](https://docs.docker.com/ai/sandboxes/configuration/credentials/#custom-secrets)).

## Boundaries that matter

“No raw key in the guest” does not mean “the agent cannot use the API.” It can direct an authenticated request to an approved endpoint. It also does not make that endpoint safe: the endpoint receives the real credential and can echo it back, exposing it to guest code. microsandbox states this exception explicitly; allow lists should therefore contain only trusted endpoints ([trusted-host boundary](https://docs.microsandbox.dev/security/secrets#what-this-does-not-protect)).

A placeholder also cannot support an algorithm that must use the raw key **inside** the guest, such as guest-side request signing. microsandbox documents that limitation directly. For either substitution model, the practical choices are to move signing to a trusted host-side mechanism or deliberately inject the raw key, which gives guest code access and abandons this isolation property; Docker’s documented proxy contract supplies outbound substitutions, not a general signing oracle ([microsandbox guest-side signing](https://docs.microsandbox.dev/sandboxes/secrets#security-boundary), [Docker proxy contract](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior)). That delivery decision is separate from at-rest storage: microsandbox SDK raw values use durable plaintext sandbox configuration, its environment-reference forms avoid storing the resolved value there, while local `sbx` uses the host stores described above.
