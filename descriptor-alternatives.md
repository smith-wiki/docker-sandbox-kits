# Closest descriptor languages—and the missing layer

These formats overlap with Kit descriptors, but define different boundaries—not one interchangeable standard.

| Language | Description and portability | Enforcer; limitation |
|---|---|---|
| **Dev Container `devcontainer.json`** — environment metadata | JSONC selects an `image`/Dockerfile/Compose service and adds `features`, mounts, setup commands, ports and `hostRequirements`. The file travels with a repository; a supported subset can travel in an OCI image’s `devcontainer.metadata` label ([spec](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainer-reference.md#metadata)). | Implementing tools configure the container; its engine applies `privileged`, `capAdd` and mounts. Excellent developer-environment interchange, but those knobs are configuration—not a runtime-neutral least-authority policy. |
| **OpenShell policy YAML** — agent access policy | Declares filesystem read/write paths, Landlock behavior, process identity, and network endpoints plus allowed binaries ([schema](https://docs.nvidia.com/openshell/reference/policy-schema)). YAML can be supplied at creation or baked into OpenShell's community base image ([default policy](https://docs.nvidia.com/openshell/reference/default-policy)). | Its gateway distributes policy and its supervisor enforces it; unlike a Kit descriptor, this is an OpenShell-specific policy, not a general OCI contract ([architecture](https://docs.nvidia.com/openshell/about/how-it-works#core-components)). |
| **Kubernetes YAML and `Sandbox` CRD** — workload/orchestration | Pod specs declare images, mounts and security context; network policy is a separate object ([Pods](https://kubernetes.io/docs/concepts/workloads/pods/), [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/)). The [Agent Sandbox `Sandbox` CRD](https://github.com/kubernetes-sigs/agent-sandbox#core-sandbox) adds a persistent, singleton agent workload with lifecycle management. | Kubernetes and its network plugin enforce the relevant resources; the CRD's controller delegates isolation to the selected sandbox runtime ([network prerequisite](https://kubernetes.io/docs/concepts/services-networking/network-policies/#prerequisites), [CRD scope](https://github.com/kubernetes-sigs/agent-sandbox#overview)). Portable among configured clusters, not as one OCI-carried access request. |
| **Compose YAML** — application runtime configuration | `compose.yaml` declares services/images, mounts, networks and secrets in a separate file ([spec](https://github.com/compose-spec/compose-spec/blob/master/spec.md#the-compose-application-model)). | A Compose implementation configures its runtime; unsupported properties may be ignored with a warning, unlike a Kit's required capabilities that must refuse launch ([support rules](https://github.com/compose-spec/compose-spec/blob/master/spec.md#requirements-and-optional-attributes), [Kit conformance](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/conformance.md#3-reporting-conformance)). |

**Decision:** use Dev Containers for development tooling, Compose for multi-service configuration, OpenShell YAML for agent access control, and Kubernetes manifests for cluster sandboxes. A Kit's distinctive promise is to bind tool content and typed access requests under one image digest; that promise is useful outside Docker only when another runtime actually enforces the requests. Nix `devShells` can reproduce tools but [do not describe sandbox permissions](https://nix.dev/manual/nix/stable/command-ref/new-cli/nix3-develop).
