# Kit declarations request authority; the runtime must enforce it

A Kit's `capabilities` list asks its host for typed, versioned behavior: network access, credentials, volumes, lifecycle hooks, and more. Under the v3 specification, an unsupported **required** request prevents launch; an unsupported optional one can be skipped. The image itself grants nothing: `docker run` does not apply its Kit annotation ([v3 capability rules](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#7-capabilities), [Docker authoring guide](https://docs.docker.com/ai/sandboxes/customize/author/#capabilities)).

A digest pins code and declarations together. A permission gate can compare normalized requests during upgrades: a new allowed host **or a removed deny** widens authority and requires approval ([permission gate](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#74-permission-surface-and-the-gate)). Across mixins, network allows and denies union; deny wins. A Kit's allow list is not necessarily the entire effective policy—Docker's defaults include broad wildcards. Inspect `sbx policy ls` ([network composition](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/capabilities/com.docker.sandbox/network-policy@2.md#composition), [security notes](https://docs.docker.com/ai/sandboxes/security/#security-considerations)).

**Implementation gap:** Docker documents that `sbx` does not apply `usb-device@1`, `privileged@1`, or `agent-sessions@1` and may create a sandbox despite an unsupported required request. Do not treat successful creation as proof of full v3 conformance ([Docker's limitation](https://docs.docker.com/ai/sandboxes/customize/author/#capabilities)). The microVM also does not protect files you deliberately mount read-write: `sbx run … .` exposes that workspace to the agent ([trust boundary](https://docs.docker.com/ai/sandboxes/security/#trust-boundaries)).
