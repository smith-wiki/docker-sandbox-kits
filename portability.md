# Portable in principle, not yet in adoption

**Verdict:** Kit v3 can technically run outside Docker, but today it is a portability opportunity rather than a demonstrated cross-runtime standard. A Kit is an ordinary OCI image carrying one descriptor annotation; any engine can transport and run the image, but ignoring that annotation discards its requested protections ([artifact contract](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#10-the-oci-layout), [OCI annotations](https://github.com/opencontainers/image-spec/blob/main/annotations.md)).

An alternative runtime must validate the descriptor, expand create-time arguments, resolve Kits in dependency order, compose and lock the image, and implement—or refuse—typed capabilities. It must enforce granted policy at an unbypassable boundary and, if it gates updates, stop permission widenings for approval. If it claims `credential@1`, it must resolve bindings from a host store and respect the chosen presentation mode: proxy-managed keys and OAuth sentinels keep secrets outside, while OAuth passthrough is an explicit downgrade ([resolution](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#53-resolution-semantics-consumer-contract), [gate](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#74-permission-surface-and-the-gate), [credentials](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior)). Reverse-DNS namespaces permit third-party capabilities, although Docker's namespace defines today's built-ins.

The open library/assembler and adapter-driven TCK lower the barrier: runtimes may claim a tested subset if unsupported required capabilities fail closed ([conformance](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/conformance.md#2-runtime-conformance)). Adoption is not established: upstream calls v3 experimental and targets finalization for Q4 2026; its run guide documents `sbx`, which itself ignores three capability types and may continue after an unsupported required request ([status and run guide](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/README.md), [limitations](https://docs.docker.com/ai/sandboxes/customize/author/#capabilities)). No independent runtime is documented in those sources; that does not prove none exists.

The Dockerfile analogy supports possibility, not momentum: Dockerfile is a recipe consumed by independent Podman/Buildah builders, while the OCI image is the shared result ([Podman](https://docs.podman.io/en/latest/markdown/podman-build.1.html)). Kit YAML likewise selects a [BuildKit frontend](https://github.com/docker/sandbox-kit-spec/blob/5fabb0a260db4fded6c2f2da76e89b7582c9b536/docs/spec/SPEC-v3.md#11-descriptor-and-content), but its descriptor remains a runtime contract. Neutrality becomes realistic with a stable spec, independent runtimes publishing TCK results, compatible resolver/lock/approval behavior, secure credential providers, and credible multi-vendor evolution. Until then, expect distribution portability before enforcement portability.
