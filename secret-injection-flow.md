# How local Docker Sandboxes inject a secret

This card describes **local `sbx` sandboxes**, not Docker's cloud-agent credential path. The short version is: the Kit declares *authority to request*, the user approves and supplies a value on the host, and a host-side HTTP(S) proxy adds that value only after the request has left the microVM. A v3 Kit descriptor contains no real key.

## From Kit declaration to provider response

Before the agent starts, `sbx` resolves two separate declarations:

- `com.docker.sandbox/credential@1` names a host-store `service`, an `install` or `runtime` `phase`, and an API-key presentation: optional in-VM variable `name`, `proxyManaged`, plus each injection `domain`, `header`, and `format`. The capability specifies how a credential is presented, **never where its value lives** ([credential capability](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md)).
- `com.docker.sandbox/network-policy@1` independently allows egress for that phase. Every injection domain must occur in the matching phase's allow-list; injection does not itself grant a connection ([network-policy validation and runtime behavior](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/network-policy@1.md)).

For a third-party Kit, the user also approves a host-side binding for the service mechanism and domains. That binding is an authorization record, not a value or a pointer to one. The value is separately held under the service identifier in the host credential store; built-in Kits shipped with `sbx` do not require this binding ([Docker: credential bindings](https://docs.docker.com/ai/sandboxes/configuration/credentials/#credential-bindings), [Docker: stored secrets](https://docs.docker.com/ai/sandboxes/configuration/credentials/#stored-secrets)). A required declaration without a binding is specified to fail resolution, although current non-interactive `sbx` instead starts with the credential withheld and warns ([spec runtime behavior](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior), [Docker: first-run approval](https://docs.docker.com/ai/sandboxes/configuration/credentials/#first-run-approval)).

An authenticated request then follows this six-step path:

1. **Inside the microVM:** for a named proxy-managed API key, the process sees a non-secret sentinel in the declared environment variable; an inject-only declaration has no variable at all. The client constructs its request using that sentinel. Install credentials exist only during install hooks; runtime credentials are the agent's steady-state grant ([credential runtime behavior](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#runtime-behavior)).
2. **Across the VM boundary:** outbound HTTP or HTTPS uses the host **forward proxy**. Docker routes all outbound TCP through the host, but non-HTTP(S) traffic takes a transparent-proxy path ([Docker architecture: networking](https://docs.docker.com/ai/sandboxes/architecture/#networking)).
3. **Policy decision:** the host boundary checks the destination against the active, phase-appropriate network policy. A denied destination stops here. Both forward and transparent proxy paths enforce policy, but **only the forward proxy injects credentials** ([Docker isolation: network isolation](https://docs.docker.com/ai/sandboxes/security/isolation/#network-isolation)).
4. **Host lookup:** for a permitted request matching the declared service/domain, the forward proxy resolves the service's value from the host-side store. The Kit declaration and approval binding do not carry that value ([Docker: how credential injection works](https://docs.docker.com/ai/sandboxes/configuration/credentials/#how-credential-injection-works)).
5. **Rewrite outside the VM:** the proxy overwrites the declared header according to `format`—for example, `Authorization: Bearer %s`—with the host value, after the request has crossed the microVM boundary. The v3 descriptor remains declarative and contains no key ([Docker authenticated-request walkthrough](https://docs.docker.com/ai/sandboxes/architecture/#follow-an-authenticated-request), [Kit v3 example](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/SPEC-v3.md#2-example)).
6. **Provider and return path:** the proxy forwards the rewritten request; the provider's response returns through the proxy to the agent. Docker's documented guarantee is that the credential remains host-side during this normal flow, not that the agent is unable to invoke the authenticated service ([Docker authenticated-request walkthrough](https://docs.docker.com/ai/sandboxes/architecture/#follow-an-authenticated-request)).

## What root in the VM can and cannot see

The agent has `sudo`, can inspect its processes, files, environment, and request before it leaves, and receives the provider response. That is intentional: in-VM privilege separation is not the security boundary. The separate kernel/microVM protects host processes and unshared files, while forced host egress supplies the network and credential controls ([Docker security model](https://docs.docker.com/ai/sandboxes/security/#trust-boundaries), [hypervisor isolation](https://docs.docker.com/ai/sandboxes/security/isolation/#hypervisor-isolation)). Thus VM root normally finds only the sentinel—not the store value or the post-boundary rewritten header—but can still make billable or state-changing calls, read returned data, and send data to every permitted endpoint. "Cannot read the raw key" is narrower than "cannot exercise its authority."

The guarantee also has explicit boundaries and escape hatches:

- A real key explicitly placed in a sandbox environment variable or file is inside the VM; proxy isolation does not erase it ([Docker credential isolation](https://docs.docker.com/ai/sandboxes/security/isolation/#credential-isolation)).
- A workspace mount exposes its contents. Even clone mode mounts the source read-only, so an untracked or ignored `.env` remains readable; read-only prevents modification, not disclosure ([Docker clone-mode warning](https://docs.docker.com/ai/sandboxes/security/isolation/#clone-mode)).
- `oauth.passthrough: true` deliberately returns the real token to the sandbox and is a documented security downgrade ([credential capability](https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md#config)).
- SSH-agent forwarding is a separate authority path. The private key stays on the host, but sandbox processes can request authentication or signatures; forwarding is enabled by default unless disabled ([Docker SSH-agent credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/#ssh-agent)).
- The approved provider necessarily receives the injected credential. If that endpoint reflects it in a response, log, or other agent-readable output, the proxy cannot make the reflected copy unknowable; destination approval is therefore part of the trust decision ([microsandbox documents the same proxy-pattern limit](https://docs.microsandbox.dev/security/secrets#what-this-does-not-protect)).

Docker's public pages document an HTTP(S) forward proxy, destination-policy checks, header rewriting, and an internal DNS resolver that enforces policy. They do **not** document enough low-level detail here to claim microsandbox's particular TLS identity, SNI matching, or DNS-pinning guarantees for Docker. Do not infer identical anti-confusion controls merely from the shared proxy pattern.

At a high level, both systems aim to leave stored secret bytes outside a microVM while granting scoped authenticated egress, but their configuration models and documented enforcement details differ.
